What was evaluated, the switch rule, and the limits

What was evaluated. The new spec-v2 harness is the slice-06 cycle-runner driving the five Grain contexts of slices 01–05. It was set the job of regenerating the full Löyly app from its spec, in shadow beside the legacy Löyly harness. In each shadow run both harnesses ran the whole cycle end to end: fence, checklist, gate, verdicts filed, score and scoreboard. They worked on shared input: one builder run (pi with its Gondolin backend) produced the candidate both gates judged, and one verdicts file was filed into both scorers. The operating session, the final judge, compared the two sides at each stage.

The switch rule was two consecutive shadow runs that the judge accepts at every stage. Runs 4 and 5 met it: both sides agreed at every stage, both scored 11/11, and the cycle ended cycle-passed. Runs 1 and 2 each found a gate defect in the new harness, and spec rounds 7c and 7d fixed them. Run 3 agreed through the gate, but its score could not be compared. The 1 procedure fix: keep the runner alive.

Limits, in one line: this proves the harness only on HTTP apps (not yet on its own stdio contexts), on one 11-item benchmark, with verdicts from a grading session instead of a sealed grader, and with a run that cannot resume after a runner restart (§7).

Evidence: .pi/harness/.state/shadow/run-01 to run-05 (git-ignored run state) and .pi/spec/decisions.md, as of branch spec-v2. Source: decisions.md, “The switch to the new harness (decided 2026-11-08)”, items 1, 3, 4 and 6; shadow/run-0N/evidence/builder/summary.txt.

It is one slice, 01-booking-core, with 11 checklist items: a weekly standing-slot booking app for one sauna (sauna F) with two dressing rooms, pukuhuone 8 and pukuhuone 9. Both sides fence the same cut, 249a90b: a scratch commit on 6d42c8e whose harness/ holds the archived legacy harness with the benchmark configuration, FENCED_PATHS="impl .pi archive/legacy-harness/cycles". Full method: what “legacy” is, digests, builder, judging

What “legacy” is. The legacy side is the archived Löyly harness, archive/legacy-harness: fence.sh, verify.sh (with check.sh and probe.sh), gen_checklist.clj, score.clj and scoreboard.clj. In each run it ran in a scratch checkout of the same cut, 249a90b. No legacy cycle of this benchmark had been recorded before, so the comparison was live: in every run both harnesses ran the whole cycle end to end, and every stage was compared side by side. On the new side the cycle also concluded. Legacy started from a fresh cycle 01 each time, with harness/cycles/ absent beforehand.

Shared inputs, by design. The switch rule compares each stage “on shared input”. Builders and graders are non-deterministic, so sharing their output makes any difference between the two sides the harness’s own.

  1. Shared inputs, checked by digest. Every run used the same configuration (benchmark-config.sh, sha256:51288e81…, equal to the cut’s harness/config.sh), the same builder instruction (sha256:d72223df…), the same contexts map (sha256:debea8ae…) and the same cut, 249a90b. Every run started on a fresh runner store, fresh legacy rooms and fresh run directories.
  2. One builder run per shadow run. pi 1.4.0 with its Gondolin extension (model openai-codex/gpt-6.1-sol, high thinking, skills and templates off) built in a room that mounted only the builder room at /workspace. The run was given a gate-attempt limit of 1, so there were no repair attempts.
  3. One candidate, byte-identical to both gates. The candidate digest was taken with the seam formula and checked equal in the runner’s candidate snapshot, the builder room, the runner’s gate room and the legacy gate room. Legacy verify.sh and the runner’s gate each judged it.
  4. One verdicts file to both scorers. A grading session drove the running candidate over HTTP and wrote verdicts for items 01-001 to 01-010. The verdicts file was then handed both to legacy score.clj/scoreboard.clj and to the runner’s hand-in-verdicts.
  5. @item-01-011 judged by the main session from the raw refusal text alone (runs 3–5), with a conflict declared: the judge had seen a spec comment that hints at an alternative slot.
  6. Per-stage comparison. The judge compared fence trees (ls-tree diff), checklists (projection onto {id, title, rule, source}), gate verdicts, per-item verdicts, scores and scoreboards. It accepted a stage or traced a disagreement to its cause.

Which runner ran: run 1 used the cycle-runner from cycle 01 (rooms/c1/slice06), run 2 the one from cycle 02, and runs 3–5 the cycle 03 candidate, the build now promoted at harness-impl/06-cycle-runner (spec at ab5d23c, round 7d; gate passed on attempt 1; score 38/38). The five contexts it drove are the promoted builds of slices 01 (cycle 02, 15/15), 02 (cycle 05, 43/43), 03 (cycle 05, 11/11), 04 (cycle 05, 76/76) and 05 (cycle 01, 4/4). Builder time per run ranged 7m22s – 9m56s, one pi session each, 21–43 tool calls.

Each finding in full

In the harness (fixed)

  • The probe got the port, not the URL (run 1). The runner ran harness/probe.sh 8901, where legacy runs APP_PROBE URL. A logging-curl replay confirmed it, and the legacy probe passed 100/100 on the same candidate. Spec gap in cycle-runner/seam.md E5. Round 7c stated every legacy argument and added @item-06-036.
  • The gate room was read-only (run 2). The candidate’s suite creates temp directories inside impl/, so it went 0/16 with EACCES; a writable copy went 16/16. Round 7d made the gate room writable by the candidate’s own scripts, with the digest taken at install, and added @item-06-037.
  • SKIP lines were read by their first word (run 2). The runner recorded skipped checks as “no”, “the”, and so on. Round 7d records the whole text after SKIP and added @item-06-038. Run 3 recorded whole sentences.
  • No resume after a restart (run 3). Verdicts handed to a restarted runner halted the run (context-did-not-respond). Procedure until fixed: keep the runner alive from start to the filed score. Still open (§7).

In the regenerated app (surprises)

  • Free-text households: “Apartment 12” was accepted as a household distinct from “12” (run 3). There is no authentication; anyone can book for any apartment (runs 4, 5).
  • Open configuration: /settings and /configure change the sauna days over HTTP with no access control (runs 3–5).
  • A third slot is granted while room remains, in all three runs. The spec speaks only of a second slot.
  • Spoofable give-up: give-up checks only the household field posted with it (runs 3, 5).
  • Invoicing “signals” are a current-state readout, not a log of raised events, so “no further charge” shows only as absence (runs 4, 5).
  • Refusal ordering: when the schedule is full, “no room” wins over the closed-day and held reasons (run 5).
  • Unlinked JSON API (/api/*), found by probing (run 4). Also a deterministic race order, where the last byte written first wins (run 4).

7Limits and open items

Each limit in full
  • The HTTP app contract only. The runner’s gate is legacy verify.sh’s contract: test.sh, start.sh PORT, an HTTP GET, the marker, and APP_PROBE URL. The harness is proved on HTTP apps like Löyly, not on JSON-RPC-over-stdio services.
  • Not self-hosting yet. The harness’s own six contexts are stdio services, still gated by harness/v2/gate.sh. Spec round 8 specifies the second contract, but until its build is cross-checked and promoted, the old gate stays in place.
  • LOYLY_* naming. Beyond the gate contract, the coupling to Löyly is cosmetic: the configuration variables are named LOYLY_*.
  • Grading is a black-box agent. Verdicts came from a grading session driving the app over HTTP (grader digest recorded as shadow-0N-grading-subagent), not from a sealed, calibrated, approved digest. A sealed Löyly grader (OG1) and the product Grader are not built.
  • The 01-011 conflict. The final judge judged @item-01-011 after seeing a spec comment hinting at the answer. The conflict is declared in each verdict but not removed.
  • No resume after a restart. A run halts if its runner restarts between gate and grading (run 3). Until this is fixed, the runner is kept alive from start to filed score.
  • Narrow benchmark. One slice with 11 items. Only two runs reached the score, and both scored 11/11, so the comparison never saw a failing item or a non-baseline scoreboard.
  • Room isolation is enforced, not specified. Gondolin keeps builders in their room today, but the spec does not yet state it.
