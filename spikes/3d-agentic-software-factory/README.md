# Phoenix Yard — regenerative software architecture

> **Throwaway prototype question:** Can an immersive world make Phoenix architecture legible as a destructive learning loop—not merely an assembly pipeline?

Three variants of the same agentic factory are switchable with `?variant=` on the existing spike route:

- `A` — **Walk the Phoenix loop.** A physics-driven operator follows intent through clean-room generation, ratification, measurement and learning.
- `B` — **Phoenix system map.** An overhead view makes the six architectural phases, durable center and disposable runtime fleet visible together.
- `C` — **Guided regeneration.** The camera follows the active product and explains one inner station at a time.

The candidate conveyor is only the inner execution path. The larger architecture is spatially distinct:

- a source/specification vault is what survives;
- the prior implementation is absent from the fenced generation path;
- four stack-specific candidates are born from one accepted contract;
- independent gates produce evidence the candidates cannot author;
- Grain retains lineage, observations and measurements at the durable center;
- an elevated return carries the delta back to intent, while generated code does not return.

The four-runtime proof comes from the repository's committed regeneration report: TypeScript `10→11`, Rust `9→11`, Java `9→11`, and Rails `0→11`, yielding `44/44` final fresh-VM verdicts without changing the product contract. It is shown as a separate completed audit, not conflated with the single historical `9/11` cycle replay.

Use `?prototype=1` to expose the floating variant switcher in a production build. In development it is always visible. `Alt` + left/right arrow changes variants without taking the arrow keys away from operator movement.

This is deliberately throwaway code on `spike/3d-agentic-software-factory`. It does not call the live Pi harness and it does not write Grain facts.

## What is real

- The C4 station names, types and relationships are parsed at runtime from the repository's `.pi/architecture.md` Container diagram.
- The factory activity replays the committed `e2e-full-1793630744537.zip` normalization in `src/e2e-replay.js`.
- The recording includes the failed first container attempt, fresh repair builder, independent 9/11 verdict, runtime signals and final recorded result.
- Löyly is the product moving through the line. Its Booking API, Booking Core, Event Store, Weekly Schedule, Heater Schedule and Billing Signals modules appear on the carrier as assembly progresses.

The replay runs at one quarter recorded speed so an operator has time to move between stations. It remains historical playback, not a claim that a new regeneration is running.

## Experience stack

- React Three Fiber renders the Three.js world.
- Rapier supplies the physical world and station colliders.
- Ecctrl supplies the physics-driven operator, keyboard movement and mobile joystick/buttons.
- Ordinary DOM overlays provide accessible controls, the replay timeline and station evidence.

## Run

```bash
cd spikes/3d-agentic-software-factory
npm install
npm run spike
```

Open <http://127.0.0.1:5173/?variant=A&prototype=1>.

While the recorded cycle plays, the operator automatically walks to the active assembly station, opens its C4 evidence briefly, and continues. Desktop controls (`WASD`/arrow keys, `Shift`, `Space`) or the mobile joystick temporarily take over; cycle-follow resumes after a short idle period. Press `E` or use Inspect to enter that station's own 3D cutaway. It renders the station's local topology directly from `.pi/architecture.md`, including named C4 containers, data stores, external systems and communication labels. A product pallet shows which Löyly components exist at that point. The evidence rail exposes ownership, responsibility boundaries, exact E2E events, artifact paths, verdicts, digests and sealed cycle bindings from the committed recording. Press `Esc` to return to the factory. Automatic cycle inspections remain compact so they do not interrupt playback.

Ecctrl 2.x accepts movement through its imperative controller API. `OperatorInput` bridges the Drei keyboard state and Ecctrl touch stores into that API; displaying controls alone does not connect them.

## Interpretation

- **Pi/ORC is the assembly line:** it moves a bound product cut through build, repair and independent inspection.
- **Löyly is the product:** C4 components emerge on its carrier as the implementation is assembled.
- **Language is the product model:** the behavior and C4 boundary stay stable while the implementation profile changes.
- **Grain is the durable product history:** it records build and observation facts but does not move the line forward.
- **Independent graders are the quality gate:** builder claims cannot author the product verdict.

The alternative factory-layout research remains in `automotive-assembly-layout-research.md`.
