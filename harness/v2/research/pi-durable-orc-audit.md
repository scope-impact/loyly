# Pi durable execution with Löyly's ORC-style audit UX

Research note, 2026-11-18. This is an architecture investigation, not a change to the accepted runner or its specification. The installed builder host pins `@earendil-works/pi-durable` **1.5.1**; the checked-out ORC submodule is `4966c8e35e3bb5939570bfc645eac52a8d18eb6e`. API conclusions below apply to those revisions. Sources are the pinned [Pi package](../../../.pi/harness/builder-host/package.json), its installed [README](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/README.md) and [types](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/dist/types.d.ts), the pinned [ORC docs](../../../orc/docs/), and this repository's replay code. The Pi source is also maintained in the [official repository](https://github.com/earendil-works/pi/tree/main/packages/durable); the pinned local package, rather than moving `main`, governs a prototype here.

## Finding

**The liked audit and replay experience is a Löyly page, not an ORC viewer.** `tools/spec/replay/build.sh` creates a self-contained HTML page. Its Clojure compiler reads Grain SQLite events, groups domain events with the ORC tick and Grain bookkeeping that produced them, orders them into stage cards and store lanes, scrubs payloads, and embeds the data for `page.js` to animate. Cycle-25/26 grading pages combine separately extracted domain events, selected ORC transitions, OTLP diagnostics, and the event-storm SVG. These choices are explicit in [replay/README.md](../../../tools/spec/replay/README.md), [main.clj](../../../tools/spec/replay/src/replay/main.clj) (`STAGES`, `group-lane`, `-main`), [page.js](../../../tools/spec/replay/src/replay/page.js), and [build_grading.clj](../../../tools/spec/replay/build_grading.clj). ORC supplies valuable execution facts, but it does not own the HTML UX.

Thus the smallest way to keep the UX is **normalize committed Pi cycle facts into the replay page's presentation model**, while labeling them as Pi facts. There is no reason to invent `sheet/tree-tick-*` events for Pi tasks. Those names mean an actual ORC execution, and ORC's tick queries, trace lineage, and `resume-in-progress!` are defined over its own event store ([ORC streaming](../../../orc/docs/STREAMING.md), “Ordering, loss, and reconnection”; [event-store patterns](../../../orc/docs/EVENT-STORE-PATTERNS.md), “Event reference”). Calling a rendered Pi timeline “ORC replay” should mean *the same Löyly audit UX*, not ORC native tick recovery.

`observeCommits` publishes changes in stored commit order, but its change array's internal order is unspecified ([types.d.ts](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/dist/types.d.ts), `CommitPublication`). Make one audit entry per phase transition, or give multiple entries explicit `ordinal`s. Use `seq` for projector watermarks and the stable audit-entry ID as the deduplication key. The `seq` is a storage sequence, **not** the wall clock and not an ORC tick ID.

### Why not Pi OpenTelemetry straight into Grain?

It is a useful **diagnostic** path, but not by itself the authoritative cycle history. Pi durable can emit `pi.durable.phase`, submit, report, checkpoint and replay telemetry through an injected `TelemetryContext`; its attributes contain IDs and control metadata, not messages, arguments or results ([Pi durable README](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/README.md), “Telemetry”). The Pi telemetry package explicitly defines spans as diagnostics rather than business state, has no built-in exporter, and leaves buffering, sampling and flushing to an application adapter ([Pi telemetry README](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-telemetry/README.md), “Principles” and “Adapters”). Löyly's current [builder host](../../../.pi/harness/builder-host/host.ts) opens the Harness without a telemetry adapter. Grain's checked-out components expose an event store and event-model API but no OTLP receiver, so “straight into Grain” would require an OTLP-to-Grain adapter and declared event types.

That adapter can record spans as `pi-cycle/diagnostic-observed` facts for timing, model/tool activity and correlation. It cannot infer a complete gate decision or verdict from a missing span, and its write is not atomic with Pi's checkpoint. Even an unsampled exporter can fail between the Pi commit and Grain append. The cycle's compact audit entry should therefore be committed with the Pi phase transition and projected into Grain with deduplication and read-back; OTel spans can enrich the same replay through `run_id`, `task_id`, and trace carrier. This is an architectural inference from the cited APIs, to verify under process kill and exporter outage.

## What ORC can provide, and what it cannot claim

ORC's native stream shows real `tick-started`, `node-started/completed`, child links, RLM iterations, and terminal events for an **ORC execution**. It is a live observation channel. Its per-subscription `:seq` detects some dropped envelopes, but upstream buffers can also drop events without a sequence gap; complete readback comes from the Grain store. Reconnection reconstructs from durable `sheet/*` events, then subscribes for new events; execution restart invokes `resume-in-progress!` on that same store ([STREAMING.md](../../../orc/docs/STREAMING.md), “The envelope,” “Ordering, loss, and reconnection”). None of this replays a Pi task. A projection of Pi facts into Grain may be a valid *domain audit projection*, but it must not be represented as `sheet/*` lifecycle events or passed to ORC recovery as though it executed them.

ORC can be a **separate analyst**. The pinned [RLM guide](../../../orc/docs/RLM-GUIDE.md), “When to use RLM,” says `:repl-researcher` is for genuinely open-ended analytical steps and is heavier than fixed code/LLM nodes. The [GEPA guide](../../../orc/docs/GEPA-GUIDE.md), “Step 1” through “Step 4,” describes optimization of named `:llm` instruction strings using train/validation examples and judge metrics; it does not optimize arbitrary Pi task code or retry policy. The analyst can consume a scrubbed Pi audit export, propose prompt changes, and run offline evaluations. It cannot silently alter a live, approved cycle. ORC's own analysis then has genuine ORC ticks and traces, separate from the Pi execution timeline.

## Two adapter designs

### A. Direct audit export to the existing replay compiler — recommended first

1. The Pi cycle task owns execution. At each **committed** stage decision it appends `loyly.cycle.audit.v1` with `{cycle_id, run_id, event_id, occurred_at, stage, attempt, actor, outcome, reason_code, parent_task_id, session_id, cut_digest, candidate_digest, evidence_ref, workflow_version}`. Put no prompt, tool output, credential, or absolute host path in this entry. Append it in the same Pi transaction that advances the task checkpoint. The existing `defineEntry`/`appendEntry` API allows application entry kinds; `TaskRuntime.commit` takes a `Tx` and stores its returned task state in that same commit ([Pi README](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/README.md), “Child Tasks”; [types.d.ts](../../../.pi/harness/builder-host/node_modules/@earendil-works/pi-durable/dist/types.d.ts), `EntryRecord`, `TaskRuntime.commit`, `Tx.appendEntry`). Verify this use in the prototype's crash test.
2. A read-only exporter scans these immutable entries from the Pi store, emits a canonical `audit.v1.jsonl`, and writes an export manifest: Pi store identity, Pi package version, workflow version, source commit/cut, first/last entry IDs, count, hash, redaction version, and export time. Re-exporting the same store should produce the same canonical event bytes (manifest export time excepted). A live `observeCommits` callback may wake the exporter but is not its source of historical completeness.
3. Extend `tools/spec/replay` with an **input adapter**, not a second page. Map `audit.v1` stages to existing story cards and stickies; preserve the current animation, event-storm board, Allure links, and scrubber. Continue to read genuine Grain domain stores for the event-storm lane where the built app emits them; Pi entries supply the cycle-control lane, not substitute domain events. Show a Pi task/session lane and a source badge. ORC analysis traces can be a second lane with actual ORC provenance. Existing `main.clj` currently requires `runner-store.sqlite`, Fressian Grain bodies, and tick grouping, so this is a real adapter and grouping change, not a command-line flag ([main.clj](../../../tools/spec/replay/src/replay/main.clj), `find-stores`, `read-store`, `group-lane`).

Benefits: one execution authority, no cross-store write in the hot path, historical replay works offline, familiar UX. Cost: a versioned audit schema and page adapter. The canonical export is derived evidence, not a second control plane.

### B. Pi facts to Grain domain events, with ORC as analyst

Project Pi audit entries into a separate Grain area such as `pi-cycle/audit-observed`. Use a declared command and schema-validated event, a source key `(pi_store_id, audit_entry_id)`, a projector watermark, and a read model. Do **not** write `sheet/*` or fake ORC `tick-id`s. This follows ORC's [events-first rule](../../../orc/docs/ORC-PRINCIPLES.md), section 8, and would let Clojure queries/RLM use the facts. The existing replay compiler could read the new domain event lane, but its tick grouping must support “Pi task” provenance without an ORC tick.

Benefits: one Clojure read model and ORC analysis can share the projected facts. Costs: a second SQLite store, projector retry/reconciliation, schema evolution, and potential audit confusion. Pi's commit and Grain's append cannot be one atomic transaction across the two stores. Therefore the projector must be **at least once** with deduplication; a watermark is advanced only after the target event can be read back. A discrepancy is reported, never hidden by fabricating a success event. This is a design inference from the two independent storage APIs, not a built-in guarantee of either library.

Recommendation: prove **A** first. Add **B** only if ORC's analyst actually needs Grain read models over Pi facts. RLM can also receive a bounded, immutable export as input, avoiding a second live event store.

## Replay semantics and trust boundaries

| Question | Rule for the prototype |
|---|---|
| What is replayed? | The page replays the historical **audit timeline**. Pi alone resumes execution. An ORC analyst run has its own native tick replay. Display these as distinct lanes. |
| Ordering? | Pi commit `seq` and audit-entry ordinal establish causal order inside one store. Use `occurred_at` only for durations and display. For Pi and ORC stores together, correlate by immutable `run_id`/evidence digest; never infer causal order from cross-store wall clocks alone. |
| Subscriber dies? | Restart by scanning committed Pi entries from the last verified entry ID. A watch/observer is a notification, not the only evidence source. Terminal tasks missing from the live graph still appear in audit entries. |
| Pi crashes between effect and checkpoint? | Reconcile the external effect by stable run/attempt/session ID before retry. Pi's README explicitly says replay-safe tools with external effects still need their own idempotency (“Calling tools from tools”). A successful page export does not prove the effect ran once. |
| Target projection dies? | Re-run idempotently from the last read-back source key. Never advance the target watermark before the target event is present. |
| What may be published? | Apply the existing [replay scrubber](../../../tools/spec/replay/src/replay/main.clj) and strengthen it with an allowlisted export schema. Scrub before ORC RLM or public HTML receives the data; do not send full Pi transcript, prompts, auth, environment, or raw tool output. The existing replay strips secret-like keys and host paths, trims long values, and fails on surviving `/Users/` or `/private/`. |
| Can the analyst improve its own grader? | Only as a proposal. Freeze grader/rubric and workflow digests for a cycle; use past cases for research, separate validation/held-out cases for selection, and human approval for a new pinned version. Current Löyly [AGENTS.md](../../../AGENTS.md) already assigns ORC immutable approved contracts and forbids exploratory transcripts crossing into a fresh builder without a contract. |

The existing grading page is also tied to *passing, clean* profiles (`build_grading.clj`'s `case-data` assertions), so a general Pi replay must render failed and interrupted runs rather than silently omit them. Grading outcomes, deterministic profile diagnostics, and Allure results should be linked by `run_id` and `item_id`; the replay must not present an LLM judgment as a gate fact. This is a required adapter behavior, inferred from the current compiler's assertions and from the spec's independent gate/score split ([replay source](../../../tools/spec/replay/build_grading.clj), [AGENTS.md](../../../AGENTS.md), “The regeneration cycle”).

## Small, decisive proof

Use a throwaway, ignored room and two fixture items; do not modify `harness-impl/` or change the approved cycle-28 grader. Pin the Pi durable version and a `cycle-task.v1` definition.

1. **Happy path:** phase task creates child builder and grader tasks; gate passes. Export audit entries twice; normalized event bytes match, and every displayed stage has a source entry ID and evidence link.
2. **Retry path:** first gate fails, fresh repair child sees only candidate/evidence, second passes. The page shows two attempts with the repair nested under attempt 1. This directly probes the current cycle-28 omission of spec items `06-023/024` ([spec.feature](../../../.pi/spec/cycle-runner/spec.feature)).
3. **Crash matrix:** kill/reopen after committed fence, during builder work, after failed gate before repair, during repair, during per-item grading, and after score before export. Verify no completed effect reexecutes, the same Pi session ID resumes where permitted, external effects reconcile, and the reconstructed replay equals the uninterrupted fixture apart from measured times. Include a three-fail terminal path and no fourth builder.
4. **Subscriber loss:** stop the exporter for several Pi commits, restart from a read-only snapshot, then live-watch. Verify each audit `event_id` appears exactly once and terminal tasks remain visible. Inject duplicate and out-of-order delivery into the optional Grain projector.
5. **UX parity:** compare side by side with `tools/spec/replay/loyly-run-03.html` and `cycle-26-grading.html`: stage story, event storm, lanes, scrubbed drill-down, timeline control, Allure links. The Pi page must distinguish `Pi task`, `Grain domain event`, `ORC analysis tick`, and `OTLP diagnostic` rather than merge their authorities.
6. **Security and inference:** seed a fake API key, absolute host path, and adversarial prompt/tool output; verify no secret reaches export, static HTML, or ORC analyst input. Run an ORC RLM analysis only against a scrubbed frozen export, and check that no tool it receives can mutate the Pi store or accepted workflow.

**Decision criterion:** choose this split only if the prototype preserves the run-03/26 audit usability, survives the crash/subscriber tests, and has fewer independently advancing workflow states than the current ORC-plus-Pi runner. Keep ORC as controller if those claims do not hold. The prototype can be evaluated without changing the accepted runner or abandoning ORC's real analysis capabilities.
