Method architecture, working note, 2026-09-02

Where a harness spec would go

The method treats documentation as the source of truth and code as a build product of it. That rule is applied to the application and has never been applied to the machinery that grades the application. This page draws the flow as it stands, then draws the same flow with the harness given the same treatment as the app: a spec it is built from, an id stamper it shares, and a ratifier it does not control. The load-bearing question is not whether to write it. It is what the harness spec is derived from, and what stops the regress.

1. The flow as it stands

Every box in the document funnel cites the one above it. That is the minimum reference rule, and it is what makes a claim checkable. One harness artefact obeys it: the checklist is derived from the spec and never hand-kept, because a hand-kept list goes stale silently. The rest of the harness cites nothing, is written by hand, and is the only thing in the repository that is never regenerated.

2. Two kinds of rule, and the scope that separates them

This began as four kinds. It collapsed to two on inspection, and the collapse is the most useful thing on this page, because it removes two files that were about to be invented.

One question separates them. Does the rule survive regeneration, or does it govern regeneration? A rule that has to come back after the implementation is wiped belongs in the spec the agent reads. A rule that watches the agent build cannot live in that spec, because the thing it constrains is the building.

Functional and non-functional are one kind. Both are product behaviour, both must come back after a wipe, both belong in a feature file the agent reads. The only difference is how many screens the rule quantifies over, and that is a field on the rule, not a category above it.

Harness and method are one kind too. A method rule with no enforcement is a hope, and its enforcement lives in a harness, so a method rule is just a harness rule that several repositories happen to share. It gets no file of its own. It gets copied, which is the honest description of how our harness reaches a second repository at all.

A correction, made while writing this. The non-functional spec was described here as living nowhere, found once by hand and then forgotten. That was wrong. One of the four implementations has had it all along: a repository-wide slice, stamped and scored every cycle, holding the rules that are true of every screen rather than of one feature. It is named for what it describes rather than for what it is, which is why it was never recognised as the non-functional spec. Nothing needs building there. One sentence in its header, saying what the file is for, would stop the next such rule being filed somewhere else.

3. What generates the harness spec

The answer

Incidents generate it, and nothing else may. Every scenario in harness/spec.feature cites a specific failure that actually happened, in the same way a wiki page cites the raw source it distils.

The five in harness/README.md are already scenarios in disguise. A weaker fence probe once passed while the reference implementation was still readable one commit back is a Given, a When and a Then that nobody has written on one line.

Why not derive it mechanically

The checklist is derived from the spec by a script because the mapping is exact: one item per scenario. An incident does not determine its own generalisation.

Going from this probe read the working tree to a probe asserts the property, never the procedure believed to imply it is a judgment, and judgments are written and cited, not generated. So the incident record is the harness's raw/, and the harness spec is its wiki.

The rule that bounds the cost

No incident, no scenario. The exact mirror of "no slice plan, no code".

This stops the harness spec from growing into a second method document. It can only contain things that have already gone wrong, which today means five scenarios, and it grows only when something new breaks. A harness spec that grows faster than the incident list is being written speculatively and should be cut back.

4. When the harness is generated, and what stops the regress

The harness is generated before the spec cut, and therefore before the app. That follows from what it is for: the fence, the gate and the instrument all have to exist and be trustworthy at the moment the app run starts, and a harness changed during a run is a moved ruler.

The regress stops one step back, not at the bottom. If the harness gets a spec, something has to check the harness that checks the app. That something is the previous cycle's harness. Version N-1 runs version N's spec against version N, and if it is not green there is no cut and no app run this cycle. This is the existing rule, done is ratified by a script the claimant does not control, applied one level up, and it terminates because it only ever needs one step, never infinitely many.

The second thing that keeps it finite is an asymmetry worth stating plainly. The app spec is a build input: the app is destroyed and rebuilt from it every cycle. The harness spec is not a build input. The harness is never destroyed, because it is the thing holding the ruler still. Its spec is a regression suite over an artefact that survives, so the destructive cut does not apply to it and must be seen not to apply to it.

6. What this costs, and what it buys

What it costs

Two spec families instead of one. Product rules where they already are, and a harness spec beside them. One more tree to keep honest, and one more place for a stale line reference to rot. The first draft of this page said three, and one of the three turned out to exist already.

A bootstrap rule to hold. Keeping the previous cycle's harness runnable is a real obligation, and the day it stops being runnable the whole ratification story is a claim again.

A first cycle with nothing behind it. Cycle one has no N-1, so its harness is ratified by a person, and that should be recorded as such rather than glossed.

What it buys

The incidents become executable. Today, deleting the object-graph check from fence.sh breaks nothing that anyone would notice. With a harness spec, removing a guard fails a scenario that names the incident it came from.

Guardrails get an expiry. A scenario has an id and a citation, so a guard whose incident belongs to a model two generations old is visible as such. This is the one thing on Ford's list phrased as a defect in our own machinery.

The tacit half gets a test. The incident list stops being prose that we hope persuades a newcomer, and becomes a thing that fails in front of them.

What it does not fix

It does not make the harness shareable across an organisation. Packaging the machinery so someone else can make new checks with it is a separate move, and this one is a precondition for it rather than a substitute.

It does not fill the informative feedback cell. Step 12 is drawn here because the loop does not close without it, but writing a harness spec does not run a single mission.

7. The socket: where a thing seen becomes a rule

Everything above is about rules written in advance. This section is about the other direction, which is the cell Ford's grid leaves thin: what happens to something noticed after the fact.

We have exactly one sensor that works, and it is not a script. It is an agent driving the real application on the real device and looking at what comes back. It is the only thing in the method that has ever found a defect a green suite could not, and it has done so every time it has been run.

What it lacks is anywhere for what it sees to go. A finding lands in a message, is fixed or is not, and evaporates. There is no id, no count, and nothing that notices the same thing being seen twice. So the next thing to build is not another sensor. It is the socket the working sensor plugs into.

One entry, with the four fields that make it more than a note:

F-02-004  a label passes while the screen is in the wrong language
observed  driving the deployed surface, cycle 02
sensor    reality audit
item      the scenario that passed for the wrong reason
becomes   that scenario reworded, at the next cut
status    closed

sensor

Which eye saw it. A finding with no sensor was seen by a person reading, which is fine, but it is not perception anyone can run again next cycle.

becomes

The link from a thing seen to a rule that now exists. This is the whole point of the file. A perception that never becomes a rule was entertainment.

status

Left open past one cycle, it is an alarm: we saw something, did nothing, and then saw it again. Same shape as an inbox that nobody drains.

The rule that makes it drain. Every finding written after a generation has, by the next cut, either become a rule or been deferred with a reason. The cut already exists as a hard boundary, since after it nothing can change until the following cycle, so the file inherits its deadline rather than needing one.

The one number it buys. Findings the instrument could not see, counted cycle over cycle. If that falls, the spec is learning. If it stays flat, we are finding new things at the rate we always did and the harness is not improving. That is a claim the current pass-rate cannot make.

The uncomfortable part, said plainly: of the three eyes designed for this, the independent review and the persona session are both unbuilt. The socket would currently be fed only by a generation's own screenshots, which is the weakest of the three, because the agent is looking at its own work.

8. Open decisions

Two are settled since the first draft. Where the non-functional spec lives is answered by section 2: it is a repository-wide slice in the same tree as every other slice, because it is the same kind of rule at a wider scope, and one implementation has been doing this all along. Whether the harness spec is Gherkin is answered yes, so that it reuses the existing stamper and the existing checklist deriver rather than growing a second format with a second parser: harness scenarios take their own file tree and their own id prefix, so the product denominator never absorbs them.

What remains open:

  1. Whether a harness scenario reads as Gherkin should. Settling on the format did not settle the register. The actor is a gate rather than a person, and Gherkin exists to be read by a domain expert who will never read one of these. The objection survives the decision, and the first few scenarios are what will show whether it matters.
  2. How a harness scenario is made RED. The application's scenarios need a fixture. A harness scenario needs a sabotaged machine: to watch the missing-tool guard fail, the tool has to be hidden on purpose. That cost was not visible until the first one was drafted.
  3. Whether step 12 runs inside or outside the build round. Inside is cheaper and is no longer an independent observation, because the agent is driving a mission over the feature it just wrote. Recorded as a decision either way, never allowed to happen by drift.
  4. Which of the four implementations goes first. The trainer has run a reality audit and the production pipeline has the only real cycle history, so those two can test the return arrow. The two sauna repositories cannot, because neither has ever produced a finding by driving anything.
